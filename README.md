# Bytecode Without the Black Magic

Demo repository for the talk **“Bytecode Without the Black Magic: Java’s Class-File API in Practice.”**

The project uses the permanent Class-File API available in JDK 25 (`java.lang.classfile`).

## Requirements

- JDK 25
- `java`, `javac`, and `javap` on `PATH`
- Maven for the Maven build, or Bash/PowerShell for the scripts

There are no application runtime dependencies.

## One output directory

Both build approaches compile the project into:

```text
target/classes
```

The generated class is also written there:

```text
target/classes/demo/generated/Generated.class
```

The transform demo replaces the compiled target class in place:

```text
target/classes/demo/target/Calculator.class
```

So every demo uses the same class tree.

## Repository layout

```text
src/main/java/
├── demo/target/Calculator.java
```

The three demos follow the talk's main progression:

```text
READ  →  GENERATE  →  TRANSFORM
```

## Build with the shell script

macOS / Linux:

```bash
./scripts/build.sh
```

Windows PowerShell:

```powershell
./scripts/build.ps1
```

The script checks that `javac` is JDK 25 and writes all compiled source classes to `target/classes`.

## Build with Maven

```bash
mvn clean compile
```

Maven uses Java release 25 and writes compiled source classes to the same standard location:

```text
target/classes
```

After either build, use the same commands below.

## Demo 1 - Inspect a compiled class

Run:

```bash
java -cp target/classes demo.inspect.InspectDemo
```

Compare the API view with `javap`:

```bash
javap -c -p target/classes/demo/target/Calculator.class
```

The interesting method is:

```java
public int add(int a, int b) {
    return a + b;
}
```

Its bytecode is recognizably equivalent to:

```text
ILOAD local[1]
ILOAD local[2]
IADD
IRETURN
```

Talking point: **a `ClassModel` gives structured access to methods, and a `CodeModel` exposes typed bytecode elements.**

## Demo 2 - Generate a class

Run:

```bash
java -cp target/classes demo.generate.GenerateDemo
```

It generates this class directly as bytecode, with no `Generated.java` in the project:

```java
package demo.generated;

public class Generated {
    public static int answer() {
        return 42;
    }
}
```

The generated class is written to:

```text
target/classes/demo/generated/Generated.class
```

Inspect it:

```bash
javap -c -p target/classes/demo/generated/Generated.class
```

The demo verifies the generated bytes with `ClassFile.verify(...)`, then loads them with an isolated class loader and 
invokes `answer()`.

Talking point: **`ClassFile.build(...)` gives you a `ClassBuilder`; method bodies are emitted through a `CodeBuilder`.**

## Demo 3 - Transform the existing Calculator class

Start from a fresh build:

```bash
./scripts/build.sh
```

or:

```bash
mvn clean compile
```

Inspect the original class:

```bash
javap -c -p target/classes/demo/target/Calculator.class
```

Run the transformation:

```bash
java -cp target/classes demo.transform.TransformDemo
```

The demo performs two transformations:

1. In `answer()`, it replaces the integer constant `42` with `43`.
2. In `add()`, it injects:

```text
[enter] add()
```

at method entry, and:

```text
[exit] add()
```

immediately before `IRETURN`.

The transformed bytes **replace the original compiled file in place**:

```text
target/classes/demo/target/Calculator.class
```

Inspect the result:

```bash
javap -c -p target/classes/demo/target/Calculator.class
```

Conceptually, `add()` becomes:

```java
public int add(int a, int b) {
    System.out.println("[enter] add()");

    int result = a + b;

    System.out.println("[exit] add()");
    return result;
}
```

The key transform is deliberately small:

```java
CodeTransform instrumentAdd = new CodeTransform() {
    @Override
    public void atStart(CodeBuilder builder) {
        emitPrintln(builder, "[enter] add()");
    }

    @Override
    public void accept(CodeBuilder builder, CodeElement element) {
        if (element instanceof Instruction instruction
                && instruction.opcode() == Opcode.IRETURN) {
            emitPrintln(builder, "[exit] add()");
        }

        builder.with(element);
    }
};
```

Talking point: **`atStart()` injects new elements before the original method body; intercepting `IRETURN` lets us 
inject code immediately before returning while preserving the original instruction.**

### Important

`TransformDemo` modifies `Calculator.class` in place. Before running the transform again, rebuild the project so you 
start from the pristine class:

```bash
./scripts/build.sh
```

or:

```bash
mvn clean compile
```

## Run the complete demo sequence

macOS / Linux:

```bash
./scripts/demo-all.sh
```

Windows PowerShell:

```powershell
./scripts/demo-all.ps1
```

The script:

1. rebuilds the source classes into `target/classes`,
2. runs the inspect demo,
3. shows the original `Calculator` with `javap`,
4. generates `Generated.class` into `target/classes`,
5. shows the generated class with `javap`,
6. transforms `Calculator.class` in place,
7. shows the transformed class with `javap`.

## Stage-safety notes

- Run the complete demo once before the talk on the exact JDK 25 installation you will use.
- Keep a terminal opened at the repository root.
- Keep `Calculator.java`, `InspectDemo.java`, `GenerateDemo.java`, and `TransformDemo.java` open in presentation order.
- Before the transform section, make sure you have done a fresh build so `Calculator.class` has not already been 
  instrumented.
- `mvn clean compile` and `./scripts/build.sh` both restore a pristine compiled `Calculator.class`.
